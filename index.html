Problem Statement & Challenge Context

Amazon ML Challenge 2026 — Business Entity Resolution

In large-scale commercial marketplaces and logistics systems, business identity data arrives asynchronously from multiple independent sources. Each source contributes partial, noisy fragments of information about the same underlying real-world commercial entity:

  • Source 1 (Reference Source): Deduplicated golden reference containing 2,206,821 training entities and 1,732,544 test entities.
  • Source 2 & Source 3 (Fragmented Inflow): Highly noisy, raw data feeds containing over 10.3 million candidate records with missing fields, OCR/typographical errors, legal suffix variations, and colloquial addresses.
  • Zero Common Foreign Keys: No shared global business registration IDs, tax numbers, or phone keys exist across datasets. Matching must rely purely on noisy text fields (Business Name, Address, and Country).
  • Open-Set Generalization: Training covers US and India, while the final evaluation test set introduces a third country, France, testing zero-shot cross-lingual robustness.

Proposed Solution: Two-Stage Hybrid Architecture

Decoupled Multi-Channel Blocking + Supervised Re-Ranking

Comparing 2.2M Source 1 records against 10.3M Source 2/3 candidates directly yields over $2.27 \times 10^{13}$ pairs, making naive pairwise comparison computationally intractable. Our solution implements an optimized two-stage design:

STAGE 1

Multi-Channel Candidate Generation (Blocking)

Inverted indexing across 4 orthographic channels: Name prefix (nm), Address token (ad), Zip/PIN digits (dg), and Structured House Numbers (hn). Generates candidate pool with >99.1% ground-truth recall while discarding 99.98% of impossible pairs.

➔
STAGE 2

Pairwise Feature Extraction & Classification

Computes dense string similarity metrics (RapidFuzz Levenshtein, CountVectorizer token Jaccard, character (3,4)-gram TF-IDF cosine, length ratios). Trained with LightGBM/XGBoost using out-of-core Parquet streaming.

➔
CALIBRATION

Macro F0.5 Optimization & Singleton Gate

Calibrates probability threshold to 0.64 (prioritizing precision over recall) and applies a strict singleton discriminator to earn maximum 1.0 points on true zero-match entities.

Key Differentiating Features

  • Raw-Punctuation House Number Parser: Extracts complex Indian and US street numbers (e.g. 16-11-23/37/A, 4/50) *before* normalization strips structural slashes.
  • Stopword-Constrained Address Channel: Filters 38 high-frequency Indian and US address stopwords (nagar, colony, road) to eliminate bucket explosion.
  • Out-of-Core Memory Streaming: Processes 7.6M pairs in chunked 50,000-row batches via SciPy CSR matrices, operating stably within a 16 GB RAM ceiling.
  • Sublinear Character TF-IDF Vectorization: Robust to typos, abbreviations, and French transliteration noise.

Technology & Tooling Stack

Exploratory Noise Observations

  • Legal Suffix Discrepancies: 36.98% of $S_1$ names have formal corporate suffixes (e.g. Pvt Ltd, Corp, Inc), whereas $S_2/S_3$ often abbreviate or drop them entirely (e.g., "Infosys Ltd" vs "Infosys").
  • Non-ASCII & Transliteration: $S_2$ and $S_3$ contain up to 15.2% non-ASCII characters, Hindi/Devanagari scripts, and Telugu transliterations that have no direct character match in English $S_1$.
  • Colloquial Address Modifiers: Addresses in India frequently incorporate landmark relative offsets: "Opp. Metro Pillar 114", "Near Hanuman Mandir", which do not appear in postal databases.
  • Open-Set Geography: The test set includes France, demanding that country matching be treated as a strict equality constraint rather than a fixed categorical one-hot encoding.

Data Preprocessing & Feature Engineering

Dual-phase transformation: structural raw-text pattern harvesting, stopword-filtered candidate blocking, and pair-aligned high-dimensional text similarity computation.

Multi-Channel Blocking Key Formulation

Eliminating quadratic $O(N^2)$ search space with 4 targeted channels

Each business record generates a set of 3-tuple blocking keys (country, channel, key_token). Records sharing any key are grouped into candidate comparison buckets:

nm Channel

Name Token Prefixes

First 3 non-numeric tokens of length $\ge 4$, truncated to 4 characters.

(IN, 'nm', 'drea') Recovers 82.4% baseline matches
ad Channel

Address Token Prefixes

Informative address words excluding 38 municipal stopwords.

(IN, 'ad', 'kavuri') +10.2% recall on name typos
dg Channel

PIN / Zip Digits

Sequences of 3 or more consecutive numeric digits.

(IN, 'dg', '500036') +4.8% recall on location clusters
hn Channel

Structured House Numbers

Extracts complex hyphen/slash patterns from unstripped text.

(IN, 'hn', '16-11-23/37/a') +1.7% high-precision recall

Zero-Leakage Group Partitioning

Entity resolution models can easily overfit if pairs belonging to the same entity cluster appear in both train and validation splits.

GroupKFold on source1_entity_id: All records and candidate matches corresponding to a given Source 1 entity are strictly confined to either train OR validation.
  • 80% Train Split: 1,765,456 S1 entities (~6.1M true pairs)
  • 20% Holdout Validation: 441,365 S1 entities (~1.5M true pairs)
  • Singletons Stratified: Exact 5.58% singleton ratio maintained in both partitions.

Evaluation & Validation

Metric formulation, mathematical analysis of precision weighting, singleton penalty mechanisms, threshold tuning curves, and error forensics.

Macro-Averaged F0.5 Metric Dynamics

Official Challenge evaluation metric with interactive simulator
F_{0.5} = \frac{(1 + 0.5^2) \times \text{Precision} \times \text{Recall}}{0.5^2 \times \text{Precision} + \text{Recall}} = \frac{1.25 \times P \times R}{0.25 \times P + R}

Precision is weighted 2× higher than recall. In business entity resolution, merging two different companies (false merge) destroys supply chain routing, while missing a secondary link is tolerated.

Singleton Impact & Error Forensics

True Singleton $\rightarrow$ Empty List = Score: 1.0
True Singleton $\rightarrow$ Any False Match = Score: 0.0

Because singletons represent 5.58% (123,247 entities) of the dataset, a single false positive on a singleton destroys 100% of that entity's credit.

Top 2 Error Modes:
  1. Commercial Complexes: Multiple unrelated stores sharing identical street addresses (e.g., shopping malls). Resolved by increasing name similarity weight.
  2. Transliteration Misses: Local language store signs written phonetically in Hindi/Telugu script. Handled via address-token blocking channel.

Methodology & Documentation

Comprehensive documentation of engineering decisions, ablation experiments, design rationale, limitations, and future architectural roadmaps.

Technical Decisions & Architectural Rationale

Key engineering choices and trade-offs
Why decouple Candidate Generation (Blocking) from Pairwise Matching?
Comparing 2.2M reference entities against 10.3M source entities produces 22.7 trillion pairwise combinations. An inverted index blocking filter reduces comparisons by 99.98% to ~15M candidate pairs, enabling rich pairwise feature computation in minutes.
Why use Character N-Gram TF-IDF instead of LLM Embeddings?
Generating 768-dim embeddings for 26.4 million noisy strings would demand hundreds of GPU hours. Sublinear character (3,4)-gram TF-IDF computed over SciPy sparse CSR matrices captures typos, prefixes, and transliterations with microsecond throughput.
Why calibrate to Probability Threshold $\tau = 0.64$?
Standard binary classification uses $\tau = 0.50$. However, because F0.5 weights precision twice as heavily as recall, elevating the threshold to 0.64 penalizes ambiguous false merges, maximizing macro-averaged leaderboard score.
How is France handled if it never appears in training data?
The pipeline avoids one-hot country encodings. Country is modeled strictly as a string matching constraint (country_1 == country_2), ensuring zero-shot generalization across any newly introduced country code in the test set.

Current Known Limitations

  • Non-Latin Script Transliteration: Stores written in native Devanagari or Telugu without English transliteration rely solely on address matching.
  • Shared Commercial Complexes: Malls, tech parks, and commercial plazas sharing identical building addresses require high name similarity to prevent false merges.
  • Extreme Single-Word Names: Very short 3-letter business names (e.g., "OM", "KFC") risk collisions if address information is omitted.

Future Architectural Roadmap

  • Phonetic Soundex/Metaphone Blocking: Integrating Soundex or Double-Metaphone into the name channel to capture accent-based misspellings.
  • Graph Community Detection: Constructing an entity resolution bipartite graph across $S_2$ and $S_3$ to enforce transitive cluster consistency.
  • Distilled Dual-Encoder Fine-Tuning: Pre-training a lightweight 6-layer transformer encoder using triplet loss with hard negatives discovered during blocking.
